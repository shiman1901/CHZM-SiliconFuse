# CHZM-SiliconFuse

Версия 0.3.1. User-mode движок управления иерархией памяти для Windows 11 x64.

## 1. Обзор

CHZM-SiliconFuse — user-mode движок, который управляет трехуровневой
иерархией памяти на настольном ПК и освобождает оперативную память для игр:

- системная память DDR4;
- видеопамять GDDR6, доступная процессору через окно Resizable BAR;
- накопитель NVMe, используемый как надежное зеркало и резервный уровень.

На машине с 16 ГБ современная игра вместе с Chrome, Steam, Discord и Telegram
может занять всю физическую память. Windows начинает выгружать игру на диск,
что дает фризы, долгие загрузки и постоянную работу с page faults. SiliconFuse
снижает это давление: холодные рабочие наборы фоновых приложений вытесняются
из DDR4, а сама игра не затрагивается.

Движок работает полностью в пространстве пользователя. Он не использует
ядерных драйверов и не изменяет системный файл подкачки. Используемые
механизмы:

- пользовательские кучи Direct3D 12: `D3D12_HEAP_TYPE_CUSTOM` с
  `CPU_PAGE_PROPERTY_WRITE_COMBINE` и `MEMORY_POOL_L1`, что дает процессору
  указатель в буфер кадра GPU через BAR1;
- некэшируемые векторные инструкции AVX2 (`_mm256_stream_si256`) для записи
  в видеопамять;
- D3D12 Copy Engine (DMA) для чтения из видеопамяти;
- штатные механизмы управления памятью Win32 и NT для рабочих наборов,
  приоритетов страниц, квот и управления процессами.

Результат — практический способ дать игре несколько гигабайт запаса на
системе с 16 ГБ без перезагрузки, без драйвера и без риска для содержимого
живых приложений.

## 2. Принцип работы

В движке два независимых контура работы. Они используют общий пул VRAM,
хранилище и реализацию хеша, но имеют разные правила безопасности.

### 2.1 Контур 1: живой игровой режим (Safe Autopilot и Game Boost Reclaim)

Это рабочий режим для реальных пользовательских приложений и игр на системах
с 16 ГБ ОЗУ.

В Live-режиме движок:

- никогда не замораживает потоки: `NtSuspendProcess` не используется;
- никогда не стирает память: `MEM_RESET` не используется;
- никогда не пишет старый снимок поверх живого процесса: `WriteProcessMemory`
  в Live-режиме запрещен;
- не использует EcoQoS, поэтому частота процессора не снижается, а видео в
  браузере и интерфейс мессенджеров не начинают лагать.

**Game-Aware VRAM Yield.** При обнаружении запущенной игры
(`Cyberpunk2077.exe` и другие) движок не выделяет 1-гигабайтные срезы в
видеопамяти. Игра сохраняет 100 процентов доступной VRAM, а движок переходит
на сжатие фоновых программ в оперативной памяти DDR4.

**Избирательная защита (Immunity Rules).** От вытеснения рабочего набора
защищены несколько ролей процессов:

- сама игра (`[GAME_IMMUNE]`);
- семейство процессов активного окна в фокусе;
- GPU-композиторы браузера (`--type=gpu-process`);
- аудио-процессы (`--type=utility`, а также процессы с активным потоком
  WASAPI, определяемым через `IAudioMeterInformation::GetPeakValue`);
- интерфейс `Telegram.exe` (`[UI_PROTECTED]`).

**Механика сжатия и пробуждения.** Перед снятием контрольного снимка в BAR1
страницы проверяются через `QueryWorkingSetEx`. Копируются только страницы с
`VirtualAttributes.Valid == 1`, то есть физически резидентные. Это исключает
генерацию десятков тысяч page faults во время снятия снимка.

Фоновым рендерерам (`chrome.exe`, `steamwebhelper.exe`, `Discord.exe`)
понижается приоритет страниц (`ProcessMemoryPriority = 1`) и выполняется
однократный сброс холодных страниц (`EmptyWorkingSet`). В жесткую квоту
(`HARDWS_MAX_ENABLE`) процессы не запираются.

При переключении окна (`Alt+Tab`, вотчер фокуса с интервалом 20 мс) функция
`WakeGroup` работает по закешированным дескрипторам и возвращает
`ProcessMemoryPriority = 5` за 0,087–0,20 мс. Границы Working Set сбрасываются
явными параметрами (1 МБ, 4096 МБ, `HARDWS_MIN_DISABLE | HARDWS_MAX_DISABLE`),
что обходит особенность ядра `ntoskrnl!MmAdjustWorkingSetSizeEx`, где пара
`(-1, -1)` вызывает `EmptyWorkingSet` вместо сброса квоты. Затем выполняется
пакетный `PrefetchVirtualMemory`.

### 2.2 Контур 2: лабораторная побитовая гибернация Hard Cryo (только `--torture-test`)

Этот контур выполняет побитовую гибернацию выделенного тестового процесса.
К живым пользовательским приложениям он не применяется.

Последовательность замораживания:

1. Целевой процесс приостанавливается (`NtSuspendProcess`) с двойной сверкой
   потоков.
2. Приватные RW-регионы читаются чанками по 64 МБ.
3. Рассчитывается контрольная сумма AVX2 `Hash64`.
4. Данные записываются в срезы GDDR6 через окно BAR1.
5. Те же данные синхронно дублируются в небуферизованное зеркало на NVMe
   (`cryo_mirror.bin`, 4 ГБ, `FILE_FLAG_NO_BUFFERING |
   FILE_FLAG_WRITE_THROUGH`, выравнивание 4096 байт).
6. Только после того, как зеркало стало durable, физические страницы ОЗУ
   сбрасываются (`MEM_RESET`).

Транзакционный журнал (`cryo_journal.bin`) фиксирует каждый переход
состояния: `PREPARED -> MIRROR_DURABLE -> SOURCE_RESET -> RESTORED`.

Последовательность восстановления:

1. Данные возвращаются из GDDR6 через DMA.
2. Проверяется хеш AVX2.
3. Поврежденные блоки автоматически лечатся из NVMe-зеркала при инверсии бита
   или потере GPU (TDR).
4. Если повреждены оба источника, движок переходит в `SAFE_LOCKOUT` и не
   возобновляет процесс.

Защита от падения движка: независимый процесс-сторож
(`--recovery-guard <pid>`) отслеживает основной процесс. Если движок
принудительно завершен (`TerminateProcess`), сторож восстанавливает все
затронутые процессы по журналу, проверяет `creation_time` против повторного
использования PID и снимает все ограничения Live-режима.

Асимметрия чтения объясняет раздельную схему: запись через BAR1 ограничена

чтение через MMIO ограничено задержкой. Поэтому движок пишет через BAR1, а
читает через Copy Engine.

## 4. Структура репозитория, сборка и режимы запуска

### 4.1 Структура репозитория

```text
CHZM-SiliconFuse/
├── src/
│   ├── main.cpp              Точка входа, драйверы тестов и замеров, сторож
│   ├── engine/               VramPool, StorageBridge, CryoSwap, CommitGuard,
│   │                         PagingManager, StandbyPurge, Hash64
│   ├── gui/                  Интерфейс GDI (740x440), интеграция с треем
│   ├── common/               Общий заголовок протокола пула user/kernel
│   └── kernel/               Только проектные заметки; код драйвера не поставляется
├── docs/                     Архитектура, whitepaper и отчеты замеров
├── build_final.bat           Сборка мастер-бинарника (MinGW-w64)
├── build_probe.bat           Сборка зонда топологии оборудования
├── build_bench.bat           Сборка замера прямого BAR1 и DMA
├── build_broker.bat          Сборка брокера лизингов WDDM
├── README.md                 Английская версия
└── README_RU.md              Этот документ
```

### 4.2 Сборка

Требования:

- Windows 11 x64;
- MinGW-w64 g++ с поддержкой C++20 (проверено на GCC 16.2.0);
- процессор с AVX2;
- GPU с включенным Resizable BAR для уровня GDDR6.

Сборка мастер-бинарника:

```bat
build_final.bat
```

Скрипт компилирует `src/main.cpp`, модули движка и GUI с флагами
`-std=c++20 -O2 -mavx2 -static`, встраивает иконку приложения через
`windres`, линкует `d3d12`, `dxgi`, `dwmapi`, `psapi`, `gdi32`, `msimg32`,
`shell32`, `user32`, `ole32` и `uuid` и записывает результат в
`build\CHZM_SiliconFuse.exe`.

### 4.3 Режимы запуска

| Команда | Назначение |
|---|---|
| `CHZM_SiliconFuse.exe` | Графический интерфейс GDI, 740x440, живая телеметрия RAM/VRAM/commit |
| `CHZM_SiliconFuse.exe --real-world-benchmark` | Замер и оптимизация на живой системе |
| `CHZM_SiliconFuse.exe --live-combat-test` | Изолированный тест фонового Chrome с живой JavaScript-нагрузкой |
| `CHZM_SiliconFuse.exe --torture-test` | Полный набор стресс-тестов Hard Cryo (этапы 7–11) |
| `CHZM_SiliconFuse.exe --release-all` | Принудительный сброс всех квот и приоритетов памяти в системе |

### 4.4 Границы применимости и ограничения

- Hard Cryo доступен только через `--torture-test` и не применяется к живым
  приложениям. Для повседневной работы безопасным путем является Live-режим.
- Движок работает только в пространстве пользователя. Он не создает блочное
  устройство, не форматирует том и не подключает и не изменяет файл подкачки.
- `StandbyPurge` требует повышенных прав. Без elevation вызов выполняется как
  залогированный no-op.
- Прием комбинации `D3D12_HEAP_TYPE_CUSTOM` с `WRITE_COMBINE` и
  `MEMORY_POOL_L1` зависит от драйвера GPU и версии WDDM. Бенчмарк проверяет
  эту комбинацию во время запуска.
- Единый 4-гигабайтный write-combined L1-аллокатор на тестовой машине
  отклоняется. Четыре среза по 1 ГБ выдаются, и движок использует срезы.
- Все цифры получены на тестовой платформе из раздела 3.1. На другом
  оборудовании результаты будут отличаться.
